Крок 2. Docker і Odoo 19

Поняття, як я їх зрозумів:

1. Odoo - платформа для керування бізнесом з модулями для продажів, складу, бухгалтерії, CRM.
2. Docker - запускає програми в ізольованому середовищі, щоб вони однаково працювали на різних комп'ютерах.
3. Образ - шаблон з усім для запуску програми: код, залежності, налаштування.
4. Контейнер - запущений екземпляр образу, ізольований від інших.
5. PostgreSQL - база даних, яка зберігає й обробляє дані.
6. Том (volume) - місце, де Docker тримає дані окремо від контейнера, щоб вони не зникали разом з ним.

Встановлення і запуск

1. Спершу встановив Odoo звичайним інсталятором. Це була помилка, бо завдання вимагало Docker. Видалив її і перезавантажив комп'ютер, щоб зникли фонові процеси.
2. Docker не запускався. Разом з Claude вирішив: встановив віртуальну машину, на якій працює Docker, командою wsl --install у PowerShell.
3. Перевірив Docker командами docker --version, docker compose version, docker ps -a. Усі спрацювали.
4. Пароль до бази поклав в окремий файл .env, а не в налаштування.
5. Створив docker-compose.yml: сервіси db (PostgreSQL 16) і odoo (Odoo 19, порт 8069), томи db-data і odoo-data.
6. Запустив docker compose up -d, перевірив docker compose ps (обидва Up). Odoo відкрилась на http://localhost:8069.

Дані не зникають

Створив в Odoo контакт "Тест перезапуску", виконав docker compose stop, потім docker compose start. Контакт залишився. Причина: дані лежать у томах, а не в контейнерах. Команд, що видаляють томи (down -v, volume rm, system prune), не використовував.

База і модулі

Запитом до бази перевірив: у базі odoo_test уже встановлені Склад, Продажі, Закупівлі, Виробництво, мова інтерфейсу українська.

Товари і специфікація

Тушка куряча, кг - сировина: облік запасів і купівля увімкнені, продажі вимкнені. Філе куряче, кг - готовий товар: облік запасів і продажі увімкнені. Специфікація: з 4 кг тушки виходить 1 кг філе.

Сценарій

Закупівлю, виробництво і продаж я виконав разом з Claude через оболонку Odoo (odoo shell), а не вручну в інтерфейсі. Документи створювались тими самими методами, що й в інтерфейсі.

Закупівля P00001: 100 кг тушки по 100 грн, 10 000 грн без ПДВ (12 000 з ПДВ 20 відсотків). Отримання WH/IN/00001 виконано.
Виробництво WH/MO/00001: 25 кг філе, списано 100 кг тушки.
Продаж S00001: 10 кг філе по 200 грн, 2 000 грн без ПДВ (2 400 з ПДВ). Відвантаження WH/OUT/00001 виконано.
Залишок: тушка 0 кг, філе 15 кг.

Звірка з папером: 100 - 100 = 0; 100 / 4 = 25, 25 - 10 = 15. Цифри збіглися.

Помітив, що собівартість філе 10 000 / 25 = 400 грн за кг, а продавали по 200, тож продаж збитковий. Це наслідок вигаданих цін, а не помилка Odoo.

Агент пояснив і визнав, що треба було попередити. Тепер він без моєї згоди .env не відкриває, правило записане в пам'ять проєкту.

grill-me і grilling. grill-me лише каже викликати grilling, потрібні обидва. Агент "допитує" мене: будує дерево рішень, ставить усі питання, які можна задати зараз, до кожного дає свою рекомендовану відповідь, факти шукає сам, а рішення віддає мені, і діє лише після мого підтвердження. Чому краще за звичайний запит: у скілі прописано формат і порядок роботи, тож поведінка щоразу однакова, а агент не береться за роботу з неповним розумінням.

Випробування grill-me. План: хочу бачити в Odoo, скільки філе виходить з однієї тушки. Агент поставив три питання. Я обрав фактичний вихід (з виконаних замовлень), показ просто в чаті, а не новим полем в Odoo, і формат "кг філе з 1 кг тушки". Результат: з замовлення WH/MO/00001 вийшло 25 кг філе зі 100 кг тушки, тобто 0,25 кг на 1 кг (25 відсотків), що збігається зі специфікацією, бо замовлення виконали точно за рецептом. Користь: без питань агент одразу побудував би поле в Odoo, а питання показало, що мені достатньо відповіді в чаті. Також він розвів плановий і фактичний вихід.

wait-what (мій скіл на вибір). Команда /wait-what: агент переказує своє попереднє повідомлення простіше, з коротким контекстом, простою технічною англійською. Я випробував: він спрацював. Спершу здавалось, що не працює, бо я чекав українську, а за SKILL.md відповідь англійською. Він ще шукає файл GLOSSARY.md, якого в мене немає, і агент це пропустив. Чужий скіл я не змінював. У скілі прописано: тільки читати, нічого не змінювати і не відправляти, ніколи не відкривати .env, зібрати коміти, незакомічені зміни і журнал, не вигадувати того, чого немає. Випробування 19 жовтня: агент виконав git log і git status, переглянув журнал, .env не відкривав. Він чесно написав, що сьогодні комітів немає (уся робота закомічена 18 жовтня) і показав два незбережені файли. Захист .env. У .claude\settings.json додав правило deny: заборона читати .env і файли, назва яких починається з .env, через вбудований інструмент читання. Обмеження: команди в терміналі (cat .env, docker compose config) правило може не зупинити, тому лишається і домовленість, що агент не відкриває .env без моєї згоди.


Репозиторій на GitHub

Посилання: https://github.com/DuckNuc/test (публічний, щоб перевіряючий відкрив за посиланням).

Головна ідея: пароль, який потрапив у Git, лишається в історії назавжди, навіть якщо файл видалити. Тому спершу забороняємо Git бачити .env, і тільки потім додаємо файли. Кроки (кожен агент пояснював перед виконанням):

1. Створив .gitignore з правилом .env (і .claude/settings.local.json).
2. Створив .env.example з тими самими назвами змінних і значенням change_me. Справжній пароль туди не копіювався.
3. git init -b main.
4. git check-ignore -v .env підтвердив, що .env ігнорується.
5. git add . і git status: у списку лише потрібні файли, .env немає.
6. Перевірки перед комітом: .env не відстежується, у доданих файлах немає значення DB_PASSWORD, у docker-compose.yml пароль лише як посилання на змінну.
7. git commit (локально, це ще не публікація).
8. Створив порожній публічний репозиторій на github.com без README і .gitignore. Програми gh на ПК не було, тому це зробив сам у браузері.
9. git remote add origin і git push -u origin main після мого окремого "так". Перевірив git ls-tree -r origin/main: .env на GitHub немає.

Дані самої Odoo (контакти, замовлення) лежать у Docker-томах поза папкою проєкту, тож у репозиторій не потрапляють.


Висновки

1. Дані в Odoo не зникають після stop і start, бо лежать у Docker-томах.
2. Сценарій закупівля, виробництво, продаж пройдено, залишки збіглися з розрахунком.
3. Секрет треба перевіряти до git add і commit, а не після, а будь-що назовні (git push) відправляти тільки після окремого підтвердження.
4. Відповіді AI треба перевіряти самому: він помилявся (маршрут, який не існує), а я помилявся, коли давав йому неправдиву інформацію.
