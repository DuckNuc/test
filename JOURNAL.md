Крок 2. Docker і Odoo 19

Спершу розібрався в поняттях, як я їх зрозумів:

1. Odoo - платформа для керування бізнесом, у ній є модулі для продажів, складського обліку, бухгалтерії, CRM та інших процесів.
2. Docker - платформа, яка запускає програми в ізольованому середовищі, щоб вони однаково працювали на різних комп'ютерах.
3. Образ - шаблон, у якому є все для запуску програми: код, залежності та налаштування.
4. Контейнер - запущений екземпляр образу, у якому програма працює ізольовано від інших.
5. PostgreSQL - система керування базами даних, яка зберігає й обробляє дані.
6. Том (volume) - місце, де Docker зберігає дані окремо від контейнера, щоб вони не зникали разом з ним.

Встановлення і запуск

Спершу я встановив Odoo 19 звичайним інсталятором, проблем не було. Але це була моя помилка, бо завдання вимагало запускати Odoo в Docker. Тому я видалив цю установку і перезавантажив комп'ютер, щоб зникли фонові процеси Odoo.

Під час встановлення Docker виникла проблема. Разом з Claude вирішив її: встановив віртуальну машину, через яку працює Docker, командою wsl --install у PowerShell.

Потім запустив Docker і перевірив, що все працює, трьома командами:

docker --version
docker compose version
docker ps -a

Усі спрацювали коректно.

Пароль до бази не писав прямо в налаштуваннях, а поклав в окремий файл .env.

Створив файл docker-compose.yml. У ньому два сервіси: db (PostgreSQL 16) і odoo (Odoo 19, порт 8069), та два томи: db-data для бази і odoo-data для файлів Odoo.

Запустив контейнери командою docker compose up -d і перевірив стан командою docker compose ps. Обидва контейнери були в стані Up.

Перевірка, що дані не зникають

Створив в Odoo контакт "Тест перезапуску". Потім зупинив контейнери командою docker compose stop і запустив знову командою docker compose start. Контакт залишився на місці.

Причина проста: дані лежать у томах, а не всередині контейнерів, тому зупинка і запуск їх не зачіпають. Команди, які видаляють томи (docker compose down -v, docker volume rm, docker system prune), я не використовував.

Чи сходяться цифри з розрахунком на папері

Так. На папері: тушки 100 мінус 100 дорівнює 0. Філе: 100 поділити на 4 дає 25 кг, 25 мінус 10 дорівнює 15 кг. В Odoo так само.

Ще помітив, що собівартість філе 10 000 грн поділити на 25 кг дає 400 грн за кг, а продавали по 200 грн за кг. Тобто продаж збитковий. Це через вигадані ціни, а не помилка Odoo.

Тепер ми домовились, що без моєї згоди він .env не відкриває, і це правило він записав у пам'ять проєкту.

Випробування grill-me

План: хочу бачити в Odoo, скільки філе виходить з однієї тушки. На той момент скіл ще не був завантажений у сесію, тому агент вів розмову за інструкцією з файлу grilling. Він поставив три питання з рекомендаціями:

1. Який вихід показувати: плановий зі специфікації чи фактичний з виконаних замовлень на виробництво? Я вибрав фактичний.
2. Де показувати? Агент радив нове поле в картці товару, а я вибрав просто в чаті.
3. У якому вигляді? Я вибрав кг філе з 1 кг тушки.

Результат: за замовленням WH/MO/00001 вироблено 25 кг філе зі 100 кг тушки, тобто 0,25 кг філе з 1 кг тушки (25 відсотків). Це збігається зі специфікацією, бо замовлення виконали точно за рецептом.

Користь скіла: без питань агент одразу почав би будувати нове поле в Odoo, бо так зрозумів фразу "хочу бачити в Odoo". Питання про те, де показувати, показало, що мені достатньо відповіді в чаті. Ще він розділив плановий і фактичний вихід.

Захист файлу .env в налаштуваннях

Після випадку з .env я захотів не покладатись лише на обіцянку агента. Створив у папці .claude файл settings.json з правилами deny: заборона читати .env і будь-які файли, назва яких починається з .env. Вони забороняють агенту читати їх через вбудований інструмент читання файлів.

Тут я теж застряг: файл у Провіднику виглядав як settings.json, але Claude Code його б не прочитав. Виявилось, що справжнє ім'я було settings.json.txt, а Windows ховає розширення файлів. Агент знайшов це командою ls і перейменував файл. Тепер у Провіднику я увімкнув показ розширень (Вигляд, Показати, Розширення імен файлів).

Важливо розуміти обмеження: це правило не гарантує повного захисту, бо команди в терміналі (наприклад cat .env або docker compose config) воно може не зупинити. Тому поруч лишається і домовленість, що агент не відкриває .env без моєї згоди.


Репозиторій на GitHub

Посилання: https://github.com/DuckNuc/test (публічний, щоб перевіряючий відкрив за посиланням).

Головна ідея. Git зберігає все, що йому додали, і після публікації пароль залишився б в історії назавжди, навіть якби файл потім видалили. Тому порядок такий: спершу забороняємо Git бачити .env, і тільки потім додаємо файли.

Кроки (агент пояснював кожен перед виконанням, команди виконувались по одній):

1. Створив .gitignore з правилом .env. Там же файл .claude/settings.local.json, бо локальні налаштування Claude Code можуть містити особисті дані.
2. Створив .env.example: ті самі назви змінних, але замість пароля change_me. Так той, хто завантажить репозиторій, знатиме, який файл створити. Справжній пароль туди не копіювався.
3. Команда git init -b main створила порожній локальний репозиторій.
4. Команда git check-ignore -v .env відповіла, що .env ігнорується правилом з .gitignore. Захист працює.
5. Команди git add . і git status: у списку сім файлів (docker-compose.yml, JOURNAL.md, .gitignore, .env.example і три скіли), справжнього .env немає.
6. Контрольні перевірки перед комітом: .env не відстежується Git, жоден доданий файл не містить справжнього значення DB_PASSWORD, у docker-compose.yml пароль є лише як посилання на змінну.
7. Команда git commit зберегла знімок на ПК. Це ще не публікація.
8. Створив порожній публічний репозиторій на github.com без README і .gitignore, щоб не було конфліктів. Програми gh на ПК не було, тому створював сам у браузері.
9. Команди git remote add origin і git push -u origin main (після мого окремого "так"). Після відправки перевірив командою git ls-tree -r origin/main, що на GitHub лежать ті самі сім файлів, а .env там немає.

Дані самої Odoo (контакти, замовлення) лежать у Docker-томах поза папкою проєкту, тому в репозиторій вони не потрапляють.

Висновок. Перевіряти, що секрет не потрапив у Git, треба до git add і commit, а не після. Відправляти щось назовні (git push) можна тільки після окремого підтвердження.
